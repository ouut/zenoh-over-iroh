# Zenoh × Iroh 项目 —— Agent 编排指令手册

> 使用方式：本手册配合《Zenoh-Iroh整合项目-完整需求文档.md》一起使用。所有 Agent 在启动任务前必须先读取该需求文档作为上下文，本手册只定义"谁在什么时候做什么、产出什么、交给谁"。

---

## 0. 编排模式说明

采用 **协调者-执行者（Coordinator–Worker）模式**：一个 Coordinator Agent 负责任务分发、验收、风险登记表维护；若干 Worker Agent 各自负责一个独立领域，通过明确定义的产出物（文件/报告）交接，不共享隐式上下文。

```
                     ┌─────────────────────┐
                     │   Coordinator Agent   │
                     │  (任务分发/验收/登记)  │
                     └──────────┬───────────┘
          ┌───────────┬─────────┼─────────┬───────────┐
          ▼           ▼         ▼         ▼           ▼
    ┌──────────┐┌──────────┐┌────────┐┌──────────┐┌──────────┐
    │接口设计   ││测试基础  ││网络    ││性能压测   ││报告与     │
    │Agent      ││设施 Agent││模拟    ││Agent      ││风险登记   │
    │(1.4节)    ││          ││Agent   ││          ││Agent      │
    └──────────┘└──────────┘└────────┘└──────────┘└──────────┘
```

每个 Worker Agent 的输出必须是**可被 Coordinator 直接验收的具体产出物**（代码/脚本/报告文件），而不是对话式总结。

---

## 1. Coordinator Agent 指令

**角色定位**：不写代码，只做任务分发、依赖排序、验收把关、风险登记表维护。

**输入**：《完整需求文档》第 3 章路线图 + 第 5 章风险登记表。

**职责**：

1. 按路线图第一/二/三批的顺序，依次向对应 Worker Agent 派发任务，**不允许跳批次并行第三批任务**（因第三批依赖自建 Relay，尚未就绪）。
2. 每个 Worker Agent 提交产出后，对照该任务对应的验收标准（需求文档 4.1/4.3 表格）逐项检查，不满足则打回并说明具体缺项。
3. 维护风险登记表（需求文档第 5 章）为活文档：任务过程中发现的新问题，必须以"编号-问题-影响-状态"的格式追加，不得口头带过。
4. 在批次之间做一次汇总检查点（Checkpoint），确认上一批次的验收标准全部达成后，才向下一批次派发任务。

**首个任务派发（第一批）**：

```
派发给【接口设计 Agent】：
  任务：在 zenoh-link-iroh 的 LinkUnicast 实现中落地需求文档 1.4 节的三态状态机设计
  依赖：无（Phase 2 代码已完成）
  产出：代码 diff + 单元测试 + 一份状态机设计说明（含状态转换图）
  验收标准：不改变对外暴露给 zenoh-transport 的公开接口签名；Migrating 态期间不上抛 Error；超时后正确上抛断连事件

派发给【测试基础设施 Agent】：
  任务：搭建对称 NAT 模拟环境 + tc netem 损伤注入脚本
  依赖：无
  产出：docker compose 拓扑编排脚本 + iptables/nftables 规则集 + 使用文档
  验收标准：能一键启动"双端对称 NAT"和"网络切换模拟"两种拓扑

派发给【网络模拟 Agent】：
  任务：执行用例 1、用例 4、用例 7（第一批）
  依赖：接口设计 Agent 的状态机代码 + 测试基础设施 Agent 的拓扑脚本（用例 4 依赖状态机代码，用例 1/7 可先行）
  产出：三份测试执行报告，含用例 4 的迁移耗时 P50/P95/P99 分布
  验收标准：见需求文档 4.1 表格对应行
```

## 2. 接口设计 Agent 指令

**角色定位**：负责需求文档 1.4 节"Migrating 三态状态机"的具体实现，是当前阶段优先级最高的任务，因为它决定后续测试是否需要返工。

**执行步骤**：

1. 阅读需求文档 1.4 节全文，特别注意"接口改动范围"约束——**不得修改对外暴露给 `zenoh-transport` 的公开 trait 签名**，状态机只能作为内部私有实现细节 + 可选回调钩子。
2. 在 `LinkUnicast` 实现中新增私有状态枚举 `LinkState { Connected, Migrating { since: Instant }, Disconnected }`。
3. 实现超时判定逻辑，超时阈值先用需求文档给出的经验值（3-5s）作为占位，并在代码中用常量/配置项标注"待用例 4/5 实测数据标定，暂用经验值"，方便后续替换。
4. 实现 `Migrating` 期间的读写行为约束（写阻塞排队、读无需特殊处理、超时后作废排队数据并上抛错误）。
5. 新增 `link.path_migrated` 可观测事件（tracing span 或 metrics counter），确认该事件不参与任何重连决策路径（做一次代码走查确认无 Zenoh 侧调用点依赖此事件触发重连）。
6. 输出：代码 diff、单元测试（至少覆盖"迁移成功回到 Connected"和"迁移超时进入 Disconnected 且数据正确作废"两条路径）、状态转换图（文字或 mermaid 均可）。
7. **禁止事项**：不要在这一步尝试实现自建 Relay 或修改 Locator 解析逻辑，这不属于本任务范围。

**产出提交给**：Coordinator Agent，用于第一批 Checkpoint。

## 3. 测试基础设施 Agent 指令

**角色定位**：负责需求文档 4.2 节描述的全部测试环境搭建，为其余 Agent 提供可复用的编排脚本。

**执行步骤**：

1. 实现 NAT 类型模拟：至少覆盖需求文档 4.2 节指定的"对称-对称""对称-端口限制"两类组合，用 `iptables`/`nftables MASQUERADE --random` 实现。
2. 实现网络损伤注入：封装 `tc netem` 常用参数（延迟/抖动/丢包/乱序/限速）为可复用脚本函数，供网络模拟 Agent 按用例调用。
3. 实现拓扑编排：优先用 `docker compose`；若后续需要多节点网状拓扑（Phase 4），预留 `mininet`/`containerlab` 的可扩展性，但**当前批次不需要真正实现网状拓扑**，只需两节点+一个官方 Relay 出口的拓扑。
4. 实现观测埋点采集通道：约定日志/metrics 输出格式（建议 JSON Lines），供报告 Agent 统一解析，不需要现在就搭建 Prometheus/Grafana，先满足"能采集到、能离线分析"即可。
5. 编写"一键启动/一键清理"脚本，避免测试之间环境状态残留污染。
6. **禁止事项**：不需要现在就做真实设备（4G热点等）回归环境的自动化，那是人工/半自动流程，只需在文档里说明如何手动执行。

**产出提交给**：Coordinator Agent，同时抄送给网络模拟 Agent 作为其依赖输入。

## 4. 网络模拟 Agent 指令

**角色定位**：负责实际执行需求文档 4.3 节列出的 9 个测试用例，按批次执行。

**前置条件检查**（执行任何用例前必须确认）：

* 用例 1/7：仅依赖测试基础设施 Agent 的拓扑脚本，接口设计 Agent 的工作**不是**前置条件，可并行开始。
* 用例 4/5：**必须等待**接口设计 Agent 的状态机代码合入后才能执行，否则测出的"恢复时间"数据没有意义。
* 用例 3/9：依赖自建 Relay 部署完成（当前阶段官方 Relay，暂不执行，留给 Phase 4）。

**执行步骤（以第一批为例）**：

1. 用例 1：双端配置为对称 NAT 拓扑，发起连接，记录打洞尝试与 Relay fallback 的时序日志，统计成功率是否达标（≥60% 直连或 100% fallback）。
2. 用例 4：在稳定连接建立后，触发网络切换模拟（禁用接口/延迟恢复），同时持续发布 Zenoh 消息，记录：
   - 状态机是否正确进入 `Migrating` 而非直接报错；
   - 恢复耗时（P50/P95/P99）；
   - 消息序号是否连续（用于后续数据完整性判断，即使本用例主要目标是耗时标定）。
3. 用例 7：固定网络条件下（无损伤），对比 Zenoh-over-TCP 与 Zenoh-over-Iroh 的小报文延迟分布。
4. 每个用例产出一份独立的测试执行报告（建议包含：测试条件、原始数据、统计结果、是否达标、异常现象记录）。

**特别注意**：用例 4 的耗时分布数据需要单独整理一份"迁移超时阈值标定建议"，明确写出建议把接口设计 Agent 代码中的占位阈值（3-5s）替换为具体数值，并回传给接口设计 Agent 更新。

**产出提交给**：Coordinator Agent，超时标定建议额外抄送接口设计 Agent。

## 5. 性能压测 Agent 指令（第二批启动后介入）

**角色定位**：负责需求文档 4.3 节用例 8（吞吐对比）及后续第三批用例 3/9（依赖自建 Relay，暂不启动）。

**执行步骤（当前仅需准备，不需要跑第三批）**：

1. 设计并实现用例 8 的压测脚本（大报文低频，1MB/10msg/s），对比 TCP 与 Iroh 的吞吐表现。
2. 预先设计（但不执行）用例 3/9 的压测方案文档：包括并发建链的梯度设计（如 10/50/100/200 并发）、Relay 侧资源监控指标清单，作为 Phase 4 启动自建 Relay 后可直接复用的方案。
3. **禁止事项**：不要在官方 Relay 上跑大规模并发压测，可能违反第三方服务的合理使用限制；用例 3/9 的实际执行必须等待自建 Relay 就绪。

**产出提交给**：Coordinator Agent。

---

## 6. 报告与风险登记 Agent 指令

**角色定位**：汇总所有 Worker Agent 的产出，生成对外可读的阶段性报告，并维护风险登记表的活文档状态。

**执行步骤**：

1. 每个批次结束后，汇总该批次所有测试执行报告，生成一份《Phase 3 第 N 批测试报告》，结构对齐需求文档 4.1 验收标准表格，逐项标注"达标/不达标/待观察"。
2. 检查是否有新发现的问题未被记录进风险登记表（需求文档第 5 章），若有，按"编号-问题-影响-状态"格式补充，编号延续 5.8、5.9……
3. 汇总用例 4/5 的耗时标定数据，形成正式的《Migrating 超时阈值标定报告》，标注最终建议值及依据。
4. 在官方 Relay 场景下产出的所有性能数据，报告中必须显著标注"基于 presets::N0 官方 Relay，未做容量压测，不作为生产容量依据"（对应风险登记表 5.4）。

**产出提交给**：Coordinator Agent，作为批次 Checkpoint 的验收材料。

## 7. 跨 Agent 协作约束（所有 Agent 通用）

1. **不得擅自扩大任务范围**：每个 Agent 只做本节指令中列出的任务，发现范围外的问题一律记录到风险登记表并上报 Coordinator，不自行处理。
2. **不得修改对外公开接口**：涉及 `zenoh-transport`/`zenoh-link` 公开 trait 的任何改动，必须先经 Coordinator 确认是否与已有对外契约冲突。
3. **产出必须是可验收的具体文件**：代码 diff、脚本、报告文档、数据文件，而非仅在对话中描述完成情况。
4. **批次边界不可跨越**：第三批相关任务（用例 3/9、自建 Relay、CI 特权 Runner、多节点网状拓扑、24h Soak Test）在自建 Relay 部署完成前不得启动执行（方案设计与准备工作除外）。
5. **发现设计冲突时的处理路径**：任何 Worker Agent 若发现需求文档中的设计（尤其 1.4 节状态机）与实测结果不符，必须先上报 Coordinator，由 Coordinator 决定是否需要打回接口设计 Agent 重新设计，不允许自行改动接口设计 Agent 的产出。
