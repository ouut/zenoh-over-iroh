# Zenoh × Iroh 整合项目 —— 完整技术需求文档

> 本文档目标：作为**唯一权威上下文来源**，使任何未参与前期讨论的工程师或 Agent，仅凭本文档即可理解项目背景、架构、已完成工作、当前阶段任务与验收标准，无需查阅历史对话记录。

## 0. 项目背景与总体目标

### 0.1 问题背景

上层业务已经在使用 **Zenoh** 的 Pub/Sub、Query/Queryable、Key-Value 抽象，但 Zenoh 默认的传输层（TCP/UDP）在复杂 NAT、移动网络场景下连通性差。**Iroh** 提供基于公钥寻址（NodeID）的 P2P 打洞穿透能力（高打洞成功率 + DERP/Relay 保底），可以作为 Zenoh 的底层 Link 实现，解决边缘设备在复杂网络下的连通性问题。

### 0.2 总体目标

* **业务无感**：上层业务代码继续使用 Zenoh 原有 API，不感知底层传输是 TCP 还是 Iroh。
* **网络无界**：依靠 Iroh 的 NodeID 寻址 + 打洞 + Relay 保底，让处于复杂 NAT/移动网络深处的设备也能连通 Zenoh 路由网络。
* **零信任安全**：跨 NAT 流量享受 Iroh 提供的端到端 TLS 1.3 / QUIC 强加密，Relay 节点全程无法解密业务数据。

### 0.3 节点分层架构图

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        Zenoh 应用业务逻辑 (Pub/Sub)                     │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 传递消息与 Key (如 demo/sensor/*)
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│               Zenoh 核心层 (Router / Peer / Session)                   │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 序列化数据帧 (Frames)
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│     zenoh-link-iroh (自定义 Transport 接口实现)                        │
│  - 解析 Locator ("iroh/<node_id>")                                     │
│  - 管理 Iroh Endpoint 与 QUIC 双向流                                    │
│  - 【新增】维护 Migrating 三态状态机，过滤路径迁移噪声                   │
└───────────────────────────────────┬────────────────────────────────────┘
```

## 1. 核心需求规格 (Requirements)

### 需求 1：自定义 Locator 寻址协议

* **格式规范**：`iroh/<node_id>`（如 `iroh/node_xyz123abc...`）。
* **功能需求**：节点配置 `connect` 或 `listen` 时，能正确识别 `iroh/` 前缀并交由 Iroh Transport 处理。

### 需求 2：`LinkUnicast` 接口实现

* **数据映射**：将 Zenoh 序列化后的 `ZBytes`/`Slice` 写入 Iroh 的 `SendStream`；从 `RecvStream` 异步读取数据交付给 Zenoh 状态机。
* **特性声明**：向 Zenoh 声明该 Link 为 **Reliable**，关闭 Zenoh 应用层多余重传机制。
* **【新增】状态机要求**：见 1.4 节，`LinkUnicast` 内部必须维护三态状态机（`Connected` / `Migrating` / `Disconnected`），不得将 QUIC 路径迁移事件直接等价映射为 Zenoh 断连事件。

### 需求 3：`LinkUnicastManager` 接口实现

* **拨号逻辑 (Dial)**：传入目标 `node_id`，调用 `iroh_endpoint.connect(target_node_id, ALPN)` 打开双向流，封装为 `LinkUnicast` 提交给 Zenoh。
* **监听逻辑 (Listen)**：后台 Task 持续等待外部传入的 Iroh 连线（监听特定 ALPN），成功后转换为 `LinkUnicast` 通知 Zenoh Runtime。

### 需求 4：异常处理与连接自愈 (Resilience)

* **网络漫游/切换**：依赖 Iroh 底层 QUIC 迁移特性，移动设备 IP 改变时连接不中断。
* **断连通知**：Iroh QUIC Stream 异常断开时，底层需及时抛出 Error 并触发 Zenoh 上层重连逻辑——**但必须经过 1.4 节的状态机过滤，不能把短暂路径切换误判为断连**。

### 1.4 【新增/关键设计】迁移中状态（Migrating）语义设计

> 背景：QUIC 的路径迁移是"连接语义不变、仅物理路径变化"，而 Zenoh 原生 Link 模型只有"活着"/"断了"二态。若不做处理，会导致要么误判断连触发不必要重连，要么迁移失败时迟迟不重连造成业务静默丢包。

**设计要点：**

1. **三态状态机**（`LinkUnicast` 内部私有状态，不对外暴露为公开接口的一部分）：

   ```
   Connected → Migrating → Connected     (迁移成功，Zenoh 无感知)
   Connected → Migrating → Disconnected  (迁移超时，才上抛真正断连)
   ```

2. **超时判定**：进入 `Migrating` 态后启动超时计时器，初始建议阈值 3–5s（需在 Phase 3 用例 4/5 中用实测 P95 迁移耗时标定，见第 4 章）。超时前不上抛任何 Error；超时后才向 Zenoh 上抛标准 Link 失效事件。

3. **读写行为**：
   * `Migrating` 期间 `write` 应阻塞/排队而非立即报错（信任 QUIC send buffer 的容忍度）。
   * `Migrating` 期间 `read` 侧无需应用层介入。
   * 若最终超时进入 `Disconnected`：排队中的未发送数据必须明确作废并上抛错误，**不得在重连后被误发到新连接**（避免消息错序/重复）。

4. **可观测性**：新增 `link.path_migrated` 类事件，仅用于日志/metrics，**不参与 Zenoh 侧重连决策**，避免影响既有对外契约。

5. **接口改动范围**：仅在 `LinkUnicastManager`/`LinkUnicast` trait 的内部实现中新增私有状态字段和可选的 `on_path_change` 回调钩子（仅供日志），**不改变对外暴露给 `zenoh-transport` 的公开接口**，确保该设计可在不推翻 Phase 2 已有对外契约的前提下落地。

## 2. 基础设施部署方案 (Relay)

| 阶段 | 方案 | 部署成本 | 说明 | 当前状态 |
| --- | --- | --- | --- | --- |
| 开发与测试阶段 | 官方预设中继 (`presets::N0`) | 0 成本 | 开箱即用 | **当前采用** |
| 生产与私有化部署 | 自建 `iroh-relay` 节点 | 低成本（1核1G VPS 起） | 官方镜像/二进制部署 | 待第三批任务触发后启动 |

**关键约束**：Relay 仅作打洞失败时的保底转发，全程无法解密内部 Zenoh 数据。

**已知风险（详见第 5 章 5.4）**：若打洞失败率显著高于预期，Relay 可能从"保底"变为"主力转发路径"，1核1G 规格可能成为吞吐瓶颈。**在得出自建 Relay 的容量结论前，所有基于官方 Relay 的性能数据必须在报告中明确标注"未做容量压测"**，不得作为生产容量依据。

## 3. 开发路线图 (Roadmap)

### Phase 1: 概念验证 (PoC) — 已完成 / 约 1-2 天

不侵入 Zenoh 内部接口，通过上层通道桥接验证连通性：启动 Iroh Endpoint → 用 `tokio::io::duplex` 桥接 Zenoh 本地通道数据到 QUIC Stream → 验证公网/复杂 NAT 下的 Pub/Sub 消息互通。

### Phase 2: 核心组件开发 (`zenoh-link-iroh`) — 已完成 / 约 3-5 天

按 Zenoh 规范实现原生 `LinkUnicast`/`LinkUnicastManager`：引入 `zenoh-link`/`zenoh-transport` 依赖 → 实现 `iroh/<node_id>` Locator 解析 → 实现数据收发（零拷贝优化）→ 实现拨号/监听逻辑。

> **注意**：1.4 节的三态状态机设计应在此阶段的接口中预留扩展点（私有状态字段 + 可选回调），避免 Phase 3 测试发现问题后需要回头改动已发布接口。

### Phase 3: 集成测试与鲁棒性验证 — **当前阶段**

详见第 4 章。**分三批执行**，而非一次性铺开全部用例：

* **第一批（优先）**：用例 1（对称 NAT 建链）+ 用例 4（网络切换）+ 用例 7（小报文延迟）。目的：验证测试基础设施可用性，同时验证 1.4 节状态机设计是否成立。
* **第二批**：用例 2/5/6（细化场景 + 数据完整性校验）+ 用例 8（大报文吞吐）。
* **第三批（可拆至 Phase 4 并行）**：用例 3/9（并发建链、Relay 容量压测，依赖自建 Relay 部署）+ 多节点网格测试 + 24h Soak Test + CI 基础设施建设。

### Phase 4（后续/待排期）

* 自建 `iroh-relay` 容量规划与压测（依赖第三批任务）。
* CI 特权 Runner 基础设施建设（独立 backlog，见 5.5）。
* 24h+ Soak Test 常态化运行（独立 backlog，见 5.7）。
* 多节点网状拓扑下的批量断连恢复测试（见 5.6）。

## 4. Phase 3 测试需求详细规格

### 4.1 测试目标与验收标准

| 维度 | 测试目标 | 量化验收标准 |
| --- | --- | --- |
| 连通性 | 对称 NAT 下端到端建链成功率 | 打洞直连成功率 ≥ 60%，Relay 保底成功率 = 100% |
| 自愈性 | 网络切换后连接恢复 | 恢复时间 P95 ≤ 5s，业务层无感知重复订阅 |
| 数据完整性 | 网络扰动期间消息不丢失/不重复 | Reliable 模式下丢失率 = 0，重复率 = 0 |
| 性能 | 与原生 TCP Link 对比开销 | 吞吐下降 ≤ 15%，P99 延迟增幅 ≤ 20% |
| 稳定性 | 长时间运行资源无泄漏 | 24h 内存增长 ≤ 5%，无 fd 泄漏 |

### 4.2 测试环境与基础设施需求

* **NAT 类型模拟**：`iptables`/`nftables` `MASQUERADE --random`，覆盖对称-对称、对称-端口限制两类高风险组合。
* **网络损伤注入**：`tc netem`（延迟/抖动/丢包/乱序/限速）。
* **多节点拓扑编排**：`docker compose` 或 `mininet`/`containerlab`，含 1 个自建 relay 节点 + N 个模拟客户端。
* **真实设备回归**：至少一组"真机 + 4G 热点 + 家用 Wi-Fi"人工/半自动回归环境，用于校准容器模拟结果（容器内 NAT 模拟无法完全代表真实运营商 CGNAT 行为，见 5.1）。
* **观测埋点**：`zenoh-link-iroh` 层（建链耗时、打洞成功/失败、Relay fallback 次数、迁移事件）+ Zenoh Session 层（断开感知延迟、重连次数、消息序号用于丢失/重复检测）。
* **自动化编排**：Rust `xtask` 或 Shell + `docker compose`，一键启动拓扑 → 运行压测负载（`z_pub`/`z_sub` 或自定义带序号负载）→ 自动采集指标 → 生成 TCP vs Iroh 对比报告。

## 5. 已知问题与风险登记表

| 编号 | 问题 | 影响 | 状态/处理方式 |
| --- | --- | --- | --- |
| 5.1 | 容器环境难以真实复现运营商级对称 NAT（CGNAT） | 容器测试成功率可能无法外推到生产 | 容器测试作为回归基线 + 保留真机多运营商测试作为最终验收依据 |
| 5.2 | QUIC 迁移与 Zenoh 重连语义冲突 | 可能导致不必要重连或静默丢包 | **已在 1.4 节给出三态状态机设计，需在第一批用例 4 中验证** |
| 5.3 | 断连感知与重连触发时序竞争 | 迁移中与重连并发时行为未定义 | 由 1.4 节的 Migrating 态统一仲裁，迁移中不对外暴露断连信号 |
| 5.4 | Relay 保底方案容量模型未验证 | 打洞失败率高时 Relay 可能成为瓶颈 | 用例 3/9（第三批）产出容量规划输入，官方 Relay 数据需标注"未压测" |
| 5.5 | CI 环境权限限制（`NET_ADMIN`） | 网络损伤类用例可能无法在标准 CI 跑 | 拆为独立 backlog，需确认是否已有自建/裸金属 Runner 可用 |
| 5.6 | 多节点网状拓扑行为未覆盖 | 点对点通过不代表网格场景无问题 | 列入 Phase 4 前置风险项 |
| 5.7 | 24h Soak Test 未计入 Phase 3 估时 | 可能成为主线交付隐性阻塞项 | 拆为独立异步任务，与 Phase 4 并行 |
| 5.8 | tc netem 100% 丢包模拟断网精度限制 | 与真实物理断网感知延迟存在差异 | 标记为已知限制，真实设备回归测试中校准 |
| 5.9 | Network namespace 需要 SYS_ADMIN 权限 | 无 Docker 环境下网络隔离受限 | 提供 namespace-setup.sh 作为备选方案，需裸机或特权容器 |
| 5.10 | Migrating 排队无深度上限 | 高频大报文可能导致内存快速增长 | 建议集成时增加 `max_queue_depth` 配置项，超限背压 |

## 6. 术语表

| 术语 | 含义 |
| --- | --- |
| NodeID | Iroh 中基于公钥的节点身份标识 |
| ALPN | Application-Layer Protocol Negotiation，QUIC 连接建立时协商的应用层协议标识 |
| Locator | Zenoh 中标识一个网络端点的地址字符串（如 `tcp/1.2.3.4:7447`，本项目扩展 `iroh/<node_id>`） |
| LinkUnicast | Zenoh 中代表一条底层单播链路的 trait 接口 |
| LinkUnicastManager | Zenoh 中负责管理链路生命周期（拨号/监听）的 trait 接口 |
| DERP/Relay | Iroh 提供的中继保底服务，打洞失败时用于转发加密流量 |
| Migrating（本项目新增语义） | `LinkUnicast` 内部状态，表示 QUIC 路径正在迁移但连接语义未失效 |
| Soak Test | 长时间运行测试，用于发现内存/句柄泄漏等累积性问题 |
